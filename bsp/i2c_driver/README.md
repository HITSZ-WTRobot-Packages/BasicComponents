# I2C DMA Driver

`bsp::I2CDriver` 提供 `I2CBusDMA`：对单条 I2C 总线暴露同步的 `memRead()` / `memWrite()` / `read()` / `write()`，底层使用 STM32 HAL DMA，并通过 CMSIS-RTOS v2 线程标志等待完成，不忙等。

## 依赖与宿主职责

- 宿主通过 CubeMX 配置 I2C、DMA、GPIO、时钟及中断，完成 HAL 初始化，并传入有效的 HAL 句柄与总线引脚描述。
- HAL 发送完成、接收完成与错误回调必须桥接到对应实例的 ISR 通知入口；缺少回调链路会导致等待超时。
- 硬件静态配置由宿主管理；不能据本包的运行期恢复流程推断其已完整校验 CubeMX 配置。

## 线程与使用限制

- 一条总线只能由一个 owner thread 串行使用，不提供多业务线程并发访问的总线仲裁。
- 同步事务只能从可阻塞的普通 CMSIS-RTOS v2 线程调用，不支持 ISR、内核启动前或裸机轮询调用。
- 设备地址参数为 7 位地址；事务结果和超时时间的精确契约见 [I2CBusDMA.hpp](I2CBusDMA.hpp) 的 Doxygen。
- 事务缓冲区及借用的 HAL 资源须覆盖其使用期；DMA 内存可访问性由宿主保证。

## 失败与恢复边界

DMA 启动失败、等待超时或当前事务收到错误完成时，本次事务仍为失败。现有实现会清理软件事务状态、尽量 abort DMA，并尝试 HAL DeInit、总线线状态恢复及 HAL Init；恢复成功不等于原事务成功。

当前实现不能可靠隔离过期完成通知：若旧 IRQ 在新事务启动后到达，可能被当作新事务完成并提前返回成功，不能据此确认新数据已经完整更新。调用方可通过 `lastError()` 与 `lastHalError()` 查询已报告的失败原因，但不能据此排除上述误归属；恢复自身也可能失败。

**现有实现与配置约定的差异：** 当前 `recover()` 的线状态恢复会临时改配 GPIO 并产生 SCL 脉冲，而非仅校验宿主配置。当前恢复实现将 SCL/SDA 按同一 GPIO 端口配置，不能将跨端口组合视为已兼容；恢复也不保证解除外部器件持续拉低的 SDA。这是需要调用方了解的现有副作用与适用限制，不是库内 GPIO 手工恢复的推荐方案。若要调整恢复策略、绕过 HAL1 或处理无法校验的配置，必须先通过 Ask 确认。
